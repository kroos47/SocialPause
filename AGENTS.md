# SocialPause project guidance

## Product contract
- Personal, offline, normal Android app for Galaxy S24 Ultra / Android 16. No Device Owner or factory reset.
- Individual mode is the upgrade/install default: App allowances default to Instagram 7 minutes and other apps 10, adjustable in one-minute steps to 0–7 and 0–12 respectively. Optional shared mode adds a combined allowance (default 20 minutes, 1–30 in one-minute steps), preserving independent app cooldowns. Mode/app edits require monitoring stopped; shared duration also requires Shared mode. Shared-sheet slider changes save immediately; Done/Back/backdrop only closes the sheet.
- Leaving an app, locking the screen, or focusing an unselected app pauses usage. The notification drawer / Quick Settings panel retains the underlying app and keeps charging it. Opening the Settings app or Recents pauses usage. No two-app cap.
- Exhausting an app starts its own continuous 60-minute cooldown immediately. Reset only that app when its deadline passes; other apps and shared consumption retain usage, focus, and deadlines. Shared exhaustion starts a separate 60-minute global block; completing it resets all app/shared allowances once.
- Lunch defaults to 14:00–15:00 unrestricted and resets usage; 15:00–16:00 blocks all selected apps, even if lunch was unused.
- A manual lunch can start once per local day, overriding any lunch/cooldown and suppressing that day’s automatic occurrence. Scheduled lunch does not consume manual eligibility. Early Stop lunch begins a full 60-minute global cooldown. Main Stop/Start, app selection and reboot must not replenish manual eligibility or replay suppressed lunch.
- Lunch edits apply today only before the old scheduled start, with no lunch started today and a strictly future new start; otherwise tomorrow. Cancel/Back/outside dismissal never saves. Preserve active overnight phases; automatic triggers during them are consumed, not replayed. Saving a lunch time enables an existing disabled schedule.
- Sleep Time defaults to 22:00–10:00: hide app timer notifications; keep enforcement active.
- Each stopped-to-running Start refreshes usage while respecting the current lunch window and locks the main Stop action for six continuous elapsed hours. Repeated Start while running must do nothing. Enforce this in the engine/controller, not just the disabled button. Home shows “Starting locks Stop for 6 hours.” while stopped and “Stop available in HH:MM:SS” while locked; at the exact deadline Stop enables without stopping monitoring. Lunch, cooldowns, sleep, and screen-off time count toward the lock. Lunch controls neither reset nor extend it. Once enabled, Stop grants unrestricted access and hides notifications.
- Ordinary process recreation, reopening, Recents removal and app updates preserve every app deadline/allowance and the Stop lock, while clearing stale focus. Reboot or confirmed Force stop leaves monitoring stopped until Start, with no timer notifications/alarms; reboot may reset ordinary usage. Use current-process startup evidence on Android 15+ for Force stop, never an old startup record or a generic process restart. When reliable evidence is unavailable, preserve state. Lunch phases, history and daily records survive. Upgrade to 0.7 preserves 0.3–0.6 timers, explicitly initializes new fields, and never applies a retrospective Stop lock to an already-running installation. The 0.3 upgrade resets old timers exactly once while preserving history, schedules, selection, running status, and current lunch restrictions.
- One ongoing notification shows the focused app, or an overview of every app when none is focused. Only active app usage requests a live status chip with explicit compact MM:SS short critical text and the drawer chronometer. In shared mode use the smaller app/shared allowance, with the SocialPause icon when shared time limits use; otherwise use the app icon; idle/cooldown uses the SocialPause icon without chip text. Use a standard template for live eligibility and custom per-app rows only for the expanded idle overview. Restore dismissed ordinary notifications while monitoring is active, except Sleep Time. Dismissing any notification must not suppress focused live promotion for the monitoring run. After dismissal over a usable selected app, restore the live request when the drawer closes, including a callback delivered after closure. From Home, retain the ordinary overview and request live promotion on entering a usable selected app. Keep charging the underlying app while the drawer is open; expose panel visibility separately from usage focus. Dismissal callbacks must retain their original surface, monitoring-run identity and notification generation; reject duplicate and obsolete events. Clear obsolete suppression preferences during upgrade without changing engine state, timers, lunch records or the six-hour Stop lock. Keep one notification ID and one bounded replacement on restoration, without repeated alerts or cancel/repost loops. Never promise an unremovable Android notification.
- Home shows a stopped-only Individual / Shared selector, shared remaining when enabled, app cards and a Lunch card with daily manual eligibility and phase controls. A sun/moon switch below Start/Stop persists appearance independently of the engine. Today Insights shows per-app used time only. Weekly bars stack app colors; selecting a day filters the total and app breakdown, not the chart. Tap the same day or outside the day targets to clear selection; scrolling must not clear it. Do not add a Show whole week button.
- Confirmed revocation of this app’s Accessibility service stops and persists monitoring even during the six-hour Stop lock, clears overlay/notification/focus, and cancels alarms. Keep this system-stop path separate from guarded user Stop. Re-enabling requires Start. A temporary disconnect while permission stays enabled preserves the run; do not treat connected=false as revocation.
- App selection must have one loading/dialog instance, one draft, validation before Save/dismissal and no stale async callback. Cancel is nonmutating.
- Usage history excludes lunch/Stop and survives resets, selection changes, upgrades, and reboot.
- Explain limitations honestly: Accessibility can redirect Home, not force-stop other apps. Normal apps are bypassable. Samsung live promotion and multi-window behavior need device testing.

## Version 0.6 design decisions
- User instructions override the V2.1 handoff: KEEP independent 60-minute app cooldowns in both modes. Only shared-budget exhaustion triggers a shared cooldown; do not implement an all-app-caps trigger or indefinite app-cap lock.
- Zero allowance means No allowance while monitoring, with no cooldown loop or invented unlock time. Lunch and overall Stop still provide unrestricted access. Positive App limit reached always has a real independent or shared cooldown deadline.
- Use hour/minute/AM–PM wheels for Lunch, with draft Save/Cancel and 0.5 conditional today/tomorrow scheduling; do not adopt the handoff's always-tomorrow rule. Keep minute-of-day conversion and overnight phase preservation in tests.
- Preserve active shared budgets above 30 minutes during upgrade. Store the clamped next-cycle configuration separately from the effective cycle allowance; individual recovery never replaces/refills shared allowance. Fresh cycle, shared reset or lunch reset adopts the new configuration.
- Keep Selected apps and permission/setup rows below the redesigned settings sections. Preserve the 0.5 focused notification icon/limiting-allowance logic and Samsung fallback.
- Theme changes affect only app appearance, never timer configuration, focus allowances, history or lunch eligibility.

## Architecture and editing
- Current implementation uses Java 17 language features and native Android Views, with no Kotlin plugin or Compose.
- Keep platform-independent rules in `engine/`. Use elapsed time for usage/cooldown, local wall time for daily schedules.
- `app/` owns Android permissions, focused-window detection, notifications, persistence, and UI.
- Preserve offline behavior: no INTERNET permission, analytics, account, or external service.
- Do not move timer logic into UI callbacks or weaken tests to get a green build.
- Keep changes limited to the requested behavior and explain the relevant files to this beginner.

## Performance contract (0.7.2)
- Keep serialized engine/history field names and types unchanged. Engine/history revisions, the date index and summary caches are transient; force the first state checkpoint after every load/migration and compare engine identity plus revisions before encoding. Actual active-use save opportunities and lifecycle transition saves must remain intact. Serialize only on the owning main thread.
- All Android settings writes go through AppController commands. MainActivity ticks read immutable snapshots and never call refresh/save/schedule. Countdown projections must not mutate the engine, cross exhaustion boundaries, reset allowances or create history.
- Window fallback: selected app or selected app under SystemUI = 500 ms; confirmed unselected unlocked app = 2 seconds; screen off = 30 seconds; stopped = no recurring inspection. Preserve the fast fallback through uncertain previously selected visibility. Batch queued window events only within a main-thread turn; lock, confirmed permission removal and dismissal visibility refresh remain immediate. Display clocks and phase/alarm scheduling are separate from window inspection. Idle schedule alarms should stay at the next boundary, including midnight, rather than slide on each update.
- Notification display signatures include visible seconds, identity, limiting allowance, row states/progress, appearance/configuration and generation. Skip formatting/building identical payloads; ordinary clock changes post at most once per elapsed second, while state changes/restoration bypass that gate. Cache labels by package/locale (safe for the app-picker worker), refresh them on package/configuration/resume events, and cache style tokens. Reconcile notifications once at startup; cancel only when entering hidden state. Retain the synchronous notification-generation checkpoint before publication and all 0.7.1 dismissal/Samsung handling.
- Reuse immutable history summaries until history, requested dates, selection or relevant configuration changes. Query only indexed dates in the requested range and rebuild the transient index after loading. Unchanged Insights must not rebuild chart data. No production diagnostic counters or personal usage data in Git. Synthetic benchmark output belongs under ignored artifacts.
- Battery claims require comparable Samsung measurements. A 75% reduction in quiet fallback checks is not a 75% battery saving; active usage still serializes history, intentionally deferred to a separate migration.

## Verification
- Read `docs/ANDROID_STUDIO.md` before changing build configuration.
- Use a complete JDK 21 or 17, including jlink, for Gradle 8.13.
- `sh scripts/verify.sh` runs timing tests, debug APK assembly, and Android lint.
- `:engine:checkRules` is a dependency-free scenario runner; an empty JUnit report does not replace it.
- For timing changes, add meaningful fake-clock scenarios for independent deadlines, delayed callbacks, lunch, process recovery, and migration. Cover the six-hour exact boundary, clock changes, rejected Stop/repeated Start, same-boot lock persistence, reboot/confirmed Force stop, and old active runs without retrospective locks. Keep the legacy serialized fixtures and randomized reference-model coverage. Include the original 0.7.1 partial/shared/cooldown/lunch/Stop-lock fixtures, revision/no-op tests, cache invalidation, midnight/week rollover, projection and adaptive scheduling tests.
- Verify notification dismissal/restoration with actual drawer swipes and Clear all as well as receiver/payload checks, including repeated clearing in both modes and returning to the same app without reopening it. Cover stale generations, callbacks after panel closure, process recreation and legacy preference migration. Verify focused/overview transitions, day selection, dark mode, and large text at runtime; separate emulator evidence from Samsung acceptance. The opt-in `RuntimeChecks` Android instrumentation uses synthetic data and must run only on a disposable emulator, never a personal phone. Build its separate APK with `:app:assembleDebugAndroidTest`; run the default payload/UI checks and the separate `-e phase drawer` real-window/gesture checks. The latter uses AOSP Clock, English controls and a 1080-pixel-wide disposable emulator; see docs/ANDROID_STUDIO.md.
- Use `python3 scripts/verify-runtime.py --serial emulator-5580` for default, gesture, cache/UI and missed-event polling suites. The wrapper must reject failed instrumentation even when adb exits zero; retain its unit tests in CI.
- Do not equate an APK build with phone acceptance. Report each separately in `docs/VALIDATION.md`.
- For the focused build/test workflow, use `.agents/skills/socialpause-build/SKILL.md`.

- The temporary Status-bar countdown diagnostic was removed after the user confirmed that Samsung Developer options → Live notifications for all apps enabled the working countdown. Keep the actual live countdown and document this phone setting; do not add the diagnostic back without a new request. Android promotion flags alone do not establish that Samsung renders a live pill. Do not force flags or fabricate Samsung support. Start with the uncolorized live format; only if this OS rejects it, try the legacy Android 16 colorized format and accept it only when the OS reports eligibility. Never apply that fallback to an ordinary notification; a restored focused live notification may request it under the same eligibility checks.

## Design reference
- V2.1 local exports are the visual reference, subject to the user-approved 0.6 hybrid rules: mint Home summary, app glyph badges, timer/state cards, compact Insights, app-colored weekly stacks, and light/dark tokens. Use real engine data, never reference sample numbers.
- Local design documents are reference material; explicit user behavior changes take precedence.
- FocusResolver owns the testable distinction between system panels and real app switches, including separate panel visibility for live-notification restoration. A panel must not clear usage focus. Read package/window metadata only, never screen text.

## GitHub publishing hygiene
- Keep signing keys, credentials, local SDK paths, real usage data, screenshots/logs, caches and generated artifacts out of Git. `.gitignore` explicitly lists the reviewed guides allowed under docs/. Review new guides before allowing them.
- Keep the Gradle wrapper JAR and synthetic `legacy-v02.bin` / `legacy-v04-*.bin` / `legacy-v05-*.bin` / `legacy-v06-*.bin` / `legacy-v071-*.bin` test fixtures. Generated `engine/bin` class files are local output, not source.
- Use portable paths in committed documentation. Check both the current files and reachable history when auditing secrets; ignore rules do not remove prior commits.
- Never rewrite published history or change Git author identity without a specific user request. Do not commit, push or force-add ignored files as part of a local audit.

- `.github/workflows/ci.yml` runs timing scenarios on Java 17/21 and application/instrumentation APK + lint checks on JDK 21. Keep actions pinned to verified commit SHAs, job permissions read-only, and PR builds free of signing credentials. Do not use `pull_request_target` to execute proposed code.
- CI APKs use disposable runner keys and must remain labelled test builds. Official personal-release APKs use the existing private local key; `.github/release-signing.sha256` contains only its public certificate fingerprint. Never upload the key or silently change that fingerprint to get a release through.
- `python3 scripts/package-release.py X.Y.Z` (also accepts `vX.Y.Z`; release notes keep the `vX.Y.Z.md` filename) requires a clean committed tree and the original key, runs full verification, checks the APK identity/certificate, and packages tracked source plus checksums under ignored `artifacts/releases/`. Publish only the four reviewed assets, after CI succeeds for that commit; never upload build logs, private keys or device captures as release assets. Keep version tags immutable.
